Creating Users and Connections

Logging in as user admin

OmniDB comes only with the user admin. If you are using the server version, the first thing to do is sign in as admin; the default password is admin. The desktop app has no sign-in at all — it runs as a single local user, so everything about user management below simply does not appear there.

Finding your way around

The whole workspace is reached from the vertical icon rail on the left edge of the window: Welcome, Connections (the plug), Database, Notify and Snippets at the top, and Getting Started, Account (server version only) and Settings (the cog) at the bottom.

Creating another user

Open Settings at the bottom of the rail and pick the Account category, then click Manage Users. Only a super user has that button — a regular user's Settings has no Account section at all.

The User management window lists the existing users. Click Add new user (the person-with-plus icon) to insert a new, blank user row, shown as (pending info) until you fill it in. Fill in the username and password, check Super User if the new user should be one, and click Save. You can create as many users as you want, edit existing ones, and delete a user by clicking the red cross in the actions column.

To sign out, click the Account icon (the person, near the bottom of the rail) and then Sign out.

The Connections section

Click the plug icon in the rail. Connections are a full section of the workspace, not a popup: a master–detail split view with the list of saved connections in the sidebar on the left and the selected connection's own form and buttons on the right.

Each row in the list shows the database engine's icon, the connection's name, and below it the user@server:port it points at (or the connection string, or the SSH target for a terminal connection). A small colored dot marks the connection's environment, and a key icon marks one that goes through an SSH tunnel.

Creating connections

OmniDB supports PostgreSQL, MySQL, MariaDB, Oracle, MS SQL Server, Firebird and SQLite, plus a Terminal connection type that opens an SSH shell instead of a database.

Click the + button under the list to create a connection. Type its name into the heading of the form on the right, choose the Connection Type, and fill in the Host Connection Info card: Server, Port, Database, User and, optionally, User Password. Instead of those individual fields you can fill in a single Connection string (for example postgresql://postgres@localhost:5432/postgres) and leave the rest blank. When you are done, click Save in the top right corner of the form.

Test Connection next to it tries the connection without opening it and reports either Connection successful. or the exact error the database returned. The − button under the list deletes the selected connection; it stays disabled for a connection that is currently open in a tab.

Passwords

The User Password field is optional, and the two choices behave differently:

  • Filled in: the password is saved into OmniDB's own configuration database and used automatically every time you open the connection. It is stored as plain text in that local database file, so treat the file as a secret — anyone who can read it can read the passwords in it.
  • Left blank: nothing is stored, and OmniDB asks for the password when you open the connection. What you type is kept only in the server's session memory for that connection, and is gone when the session ends.

For PostgreSQL, OmniDB also looks the password up in your .pgpass file at connect time, matching the same entry libpq would, so a connection with no stored password can still open without a prompt. In the sandboxed macOS app the password prompt offers Grant access to .pgpass…: you point at the file once and every later connection resolves its own password from it.

If the database refuses the attempt, the prompt stays on screen showing the error OmniDB got (fe_sendauth: no password supplied, an authentication failure, a server that is down, and so on), so you can correct the password and try again.

Importing connections from .pgpass

The file-import icon next to the + and − buttons reads a .pgpass file and creates one PostgreSQL connection per concrete line in it, as a bare postgresql://user@host:port/db connection string with no password stored — the point being to keep authenticating from that file rather than copying passwords into OmniDB. Wildcard (*) lines are skipped, and so is any line that already matches an existing connection.

Organizing the list

  • Order: drag a row to any slot in the list. The arrangement is stored per user and survives a reload and a restart. Connections you create later are added at the bottom.
  • Groups: the selector at the top of the sidebar filters the list down to one group. + Group creates a group, and the … button next to it offers Rename, Manage Connections (turns the rows into checkboxes so you can pick which connections belong to the group, then Save changes) and Delete.
  • Public connections: the Public connection? switch in the form makes a connection usable by every other OmniDB user. The Public (n) switch at the bottom of the sidebar shows or hides other users' public connections in your own list.
  • Environment: tagging a connection Production, UAT, Development or Archive colors its dot in the list and the edge of its open tab — mainly a safety cue, so reaching for the wrong tab is visibly obvious.

Opening a connection

Click Connect in the form, or simply double-click a row in the list, and OmniDB opens it in a new Connection Outer Tab as we can see in the next chapter. Right-clicking a row opens a context menu (Connect/Edit/Delete — Delete is omitted for a connection that is already open), and right-clicking empty space in the list offers New Connection/Refresh.

Using SSH tunnels

OmniDB allows the user to connect to any remote database through SSH tunnels. Tick Use SSH tunnel in the connection's own form — that enables the fields below it:

  • SSH Server: The server you are connecting to via SSH;
  • SSH Port: The port of the SSH server (default is 22, but it can be any port number);
  • SSH User: The operating system user name you use to connect to the SSH server;
  • Password/Passphrase: The password of the operating system user (or the passphrase for the key below). Leave it blank and OmniDB asks for it each time the tunnel is opened, without storing it. If you fill the field SSH Key Text File, a password is optional;
  • SSH Key Text File: The contents of the local private SSH key you can use to connect to the SSH server. OmniDB reads the file you pick and stores its text, not the file itself. If you fill this field, then you can also fill the field Password/Passphrase, but in this case it will be the passphrase for the SSH private key.

Everything you do store here — the SSH password, the passphrase and the key text — is kept in the same local OmniDB configuration database as the database passwords, and in the same plain form.
