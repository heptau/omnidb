Roles and Permissions

The Permissions section is a role and privilege browser for PostgreSQL. It lays a server's roles out Finder-style, in side-by-side columns: pick a role on the left, and the columns to its right show who it is a member of, who is a member of it, and what it can actually do on every database object — including everything it only has indirectly, through inherited role memberships or through PUBLIC. Roles, memberships and privileges can be created, changed and revoked right there.

Note: this section currently supports PostgreSQL only. For any other connection it shows Permissions are not yet supported for … / Currently only PostgreSQL is supported.

Opening the section

Click the Permissions icon (the people icon) in the left rail. The section works on a connection that is already open in the Database section: the same strip of open connection tabs is shown at its top, and the section uses whichever connection tab is selected there. With no connection open it shows No connection open — open one first (see Managing Databases). The columns are rebuilt every time you enter the section, so any earlier selection is reset.

Everything you do here needs the same privileges the equivalent SQL would need (CREATEROLE, superuser, or ownership of the object, depending on the action) — OmniDB runs the statements with the credentials of the connection you are using.

Column 1: Roles

The Roles column lists every role on the server, including the built-in pg_* roles, sorted by name. Roles that can log in (users) have a single-person icon; roles that cannot (groups) have a two-person icon. The first row is always PUBLIC (globe icon) — not a real role, but the pseudo-role every role implicitly belongs to, so that privileges granted to PUBLIC can be browsed and edited the same way.

Click a role to focus it; the other columns then show that role. Below the list:

  • + opens the Create Role dialog: Role name, Password, and the attribute checkboxes Can log in (on by default), Superuser, Can create databases, Can create roles, Inherits privileges of roles it is a member of (on by default), Can initiate replication and Bypasses row-level security, plus Connection limit (-1 = unlimited) and Account expires (leave empty for no expiration).
  • − drops the selected role (disabled for PUBLIC).

Right-clicking a role (not PUBLIC) offers:

  • Change Password — asks for the new password twice. The password is hashed in the format the server itself is configured for (SCRAM-SHA-256 or md5) before it is sent.
  • Alter Attributes — the same attribute fields as Create Role, pre-filled with the role's current values. Clearing Account expires removes the expiration.
  • Drop Role — asks Drop role "…"? This cannot be undone. and then runs a plain DROP ROLE; PostgreSQL refuses it while the role still owns objects or holds privileges.

Column 2: memberships

The second column is split in two halves:

  • … — Members (top): the roles that are members of the focused role.
  • … — Member of (bottom): every role the focused role belongs to, directly or through other roles, flattened into one list. PUBLIC is always listed first.

In both halves, direct memberships are shown in normal text and indirect (inherited) ones greyed out. A direct membership granted WITH ADMIN OPTION is marked (admin option). For PUBLIC both halves just say PUBLIC is not a member of any role.

  • The + under Member of opens Grant Membership: pick a role to make the focused role a member of it, optionally With admin option.
  • The + under Members opens Add Member: the same dialog the other way round — the picked role becomes a member of the focused role.
  • − (or right-click → Remove Membership) revokes a membership after asking Revoke membership in "…"?. Only direct memberships can be removed; an inherited one has to be revoked where it is actually granted.
  • Double-clicking a row, or right-click → Set as Active Role, makes that role the focused one, exactly as if you had clicked it in the Roles column — the quickest way to follow an inheritance chain upwards.

Column 3: objects and effective privileges

The third column, … — Objects, is a tree of everything the focused role has any privilege on — its effective privileges: its own direct grants plus everything it inherits through its memberships and through PUBLIC. It starts with two groups, Databases (every database on the server) and Tablespaces; a node is shown normally if the role has some privilege there, and greyed out otherwise.

Expanding a database loads its objects over a separate connection to that database (the connection tab's own active database does not change): schemas, and inside each schema folders for tables, views, sequences, functions, procedures, materialized views, types and domains; foreign data wrappers and foreign servers sit directly under the database. Only objects the role actually has a privilege on are listed (system schemas are left out); a schema shown greyed out is there only because something inside it is. If there is nothing at all, the database shows No privileges on any object in this database.

Editing privileges

Right-click a database, tablespace, schema or object and choose Edit Privileges. The dialog lists every privilege valid for that kind of object as a checkbox:

  • database: CREATE, CONNECT, TEMPORARY; tablespace: CREATE; schema: CREATE, USAGE;
  • table, view and materialized view: SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER;
  • sequence: USAGE, SELECT, UPDATE; function and procedure: EXECUTE; type, domain, foreign data wrapper and foreign server: USAGE.

Each checkbox tells you where the privilege comes from:

  • checked — the role holds it directly; uncheck it to REVOKE it;
  • checked but disabled, with Inherited from: … — the role only has it through another role or PUBLIC. It cannot be revoked here; make the source role active (Set as Active Role) and revoke it there;
  • unchecked — the role does not have it; check it to GRANT it directly.

With grant option applies to the privileges you newly grant in that dialog. Confirm with the dialog's main button, which is labelled with the object's name.

To grant something on an object that is not in the tree yet, use the + (Add Object Privilege) under the column: choose the Object Type, then the Database (for everything except databases and tablespaces; it defaults to the connection's current database), the Schema for schema-level objects, the Object itself (functions are shown with their argument signature), tick the Privileges and, optionally, With grant option.

Selecting PUBLIC in the first column lets you edit what is granted to PUBLIC itself (GRANT … TO PUBLIC / REVOKE … FROM PUBLIC).

Important: every action in this section is executed on the server immediately — there is no SQL preview and no undo. Only Drop Role and Remove Membership ask for confirmation first. If the server rejects a statement, its error message is shown.
