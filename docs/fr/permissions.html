Rôles et autorisations

La section Autorisations est un navigateur de rôles et de privilèges pour PostgreSQL. Elle présente les rôles d’un serveur à la manière du Finder, en colonnes côte à côte : choisissez un rôle à gauche, et les colonnes à sa droite montrent de quels rôles il est membre, quels rôles sont membres de lui, et ce qu’il peut réellement faire sur chaque objet de la base de données — y compris tout ce dont il ne dispose qu’indirectement, par le biais d’appartenances à des rôles héritées ou de PUBLIC. Les rôles, les appartenances et les privilèges peuvent être créés, modifiés et révoqués directement à cet endroit.

Remarque : cette section ne prend actuellement en charge que PostgreSQL. Pour toute autre connexion, elle affiche Les permissions ne sont pas encore prises en charge pour … / Seul PostgreSQL est actuellement pris en charge.

Ouvrir la section

Cliquez sur l’icône Autorisations (l’icône représentant des personnes) dans la barre de navigation de gauche. La section fonctionne sur une connexion déjà ouverte dans la section Base de données : la même bande d’onglets de connexion ouverts est affichée en haut, et la section utilise l’onglet de connexion qui y est sélectionné. Si aucune connexion n’est ouverte, elle affiche Aucune connexion ouverte — ouvrez-en d’abord une (voir Gérer les bases de données). Les colonnes sont reconstruites chaque fois que vous entrez dans la section ; toute sélection antérieure est donc réinitialisée.

Tout ce que vous faites ici nécessite les mêmes privilèges que le SQL équivalent (CREATEROLE, superutilisateur ou propriété de l’objet, selon l’action) — OmniDB exécute les instructions avec les identifiants de la connexion que vous utilisez.

Colonne 1 : Rôles

La colonne Rôles liste tous les rôles du serveur, y compris les rôles intégrés pg_*, triés par nom. Les rôles qui peuvent se connecter (utilisateurs) ont une icône à une personne ; ceux qui ne le peuvent pas (groupes) ont une icône à deux personnes. La première ligne est toujours PUBLIC (icône de globe) — ce n’est pas un vrai rôle, mais le pseudo-rôle auquel chaque rôle appartient implicitement, afin que les privilèges accordés à PUBLIC puissent être consultés et modifiés de la même manière.

Cliquez sur un rôle pour le rendre actif ; les autres colonnes affichent alors ce rôle. Sous la liste :

  • + ouvre la boîte de dialogue Créer un rôle : Nom du rôle, Mot de passe, et les cases d’attributs Peut se connecter (cochée par défaut), Superutilisateur, Peut créer des bases de données, Peut créer des rôles, Hérite des privilèges des rôles dont il est membre (cochée par défaut), Peut lancer la réplication et Contourne la sécurité au niveau des lignes, ainsi que Limite de connexions (-1 = illimitée) et Expiration du compte (laisser vide pour aucune expiration).
  • − supprime le rôle sélectionné (désactivé pour PUBLIC).

Un clic droit sur un rôle (autre que PUBLIC) propose :

  • Changer le mot de passe — demande deux fois le nouveau mot de passe. Le mot de passe est haché dans le format pour lequel le serveur lui-même est configuré (SCRAM-SHA-256 ou md5) avant d’être envoyé.
  • Modifier les attributs — les mêmes champs d’attributs que Créer un rôle, préremplis avec les valeurs actuelles du rôle. Vider Expiration du compte supprime l’expiration.
  • Supprimer le rôle — demande Supprimer le rôle « … » ? Cette action est irréversible. puis exécute un simple DROP ROLE ; PostgreSQL le refuse tant que le rôle possède encore des objets ou détient des privilèges.

Colonne 2 : appartenances

La deuxième colonne est divisée en deux moitiés :

  • … — Membres (en haut) : les rôles qui sont membres du rôle actif.
  • … — Membre de (en bas) : tous les rôles auxquels appartient le rôle actif, directement ou par l’intermédiaire d’autres rôles, réunis en une seule liste. PUBLIC figure toujours en premier.

Dans les deux moitiés, les appartenances directes sont affichées en texte normal et les appartenances indirectes (héritées) en grisé. Une appartenance directe accordée WITH ADMIN OPTION est signalée par (option d’administration). Pour PUBLIC, les deux moitiés indiquent simplement PUBLIC n’est membre d’aucun rôle.

  • Le + sous Membre de ouvre Accorder l’appartenance : choisissez un rôle dont le rôle actif deviendra membre, éventuellement Avec option d’administration.
  • Le + sous Membres ouvre Ajouter un membre : la même boîte de dialogue dans l’autre sens — le rôle choisi devient membre du rôle actif.
  • − (ou clic droit → Retirer l’appartenance) révoque une appartenance après avoir demandé Révoquer l’appartenance à « … » ?. Seules les appartenances directes peuvent être retirées ; une appartenance héritée doit être révoquée là où elle est réellement accordée.
  • Un double clic sur une ligne, ou clic droit → Définir comme rôle actif, fait de ce rôle le rôle actif, exactement comme si vous aviez cliqué dessus dans la colonne Rôles — le moyen le plus rapide de remonter une chaîne d’héritage.

Colonne 3 : objets et privilèges effectifs

La troisième colonne, … — Objets, est une arborescence de tout ce sur quoi le rôle actif possède un privilège quelconque — ses privilèges effectifs : ses propres droits accordés directement, plus tout ce qu’il hérite par ses appartenances et par PUBLIC. Elle commence par deux groupes, Bases de données (toutes les bases de données du serveur) et Tablespaces ; un nœud est affiché normalement si le rôle y possède un privilège, et en grisé sinon.

Le dépliage d’une base de données charge ses objets via une connexion distincte à cette base (la base active de l’onglet de connexion ne change pas) : les schémas et, dans chaque schéma, des dossiers pour les tables, vues, séquences, fonctions, procédures, vues matérialisées, types et domaines ; les wrappers de données distantes (foreign data wrappers) et les serveurs distants se trouvent directement sous la base de données. Seuls les objets sur lesquels le rôle possède réellement un privilège sont listés (les schémas système sont exclus) ; un schéma affiché en grisé n’est présent que parce qu’un élément qu’il contient l’est. S’il n’y a rien du tout, la base de données affiche Aucun privilège sur aucun objet de cette base de données.

Modifier les privilèges

Faites un clic droit sur une base de données, un tablespace, un schéma ou un objet et choisissez Modifier les privilèges. La boîte de dialogue liste sous forme de cases à cocher chaque privilège valide pour ce type d’objet :

  • base de données : CREATE, CONNECT, TEMPORARY ; tablespace : CREATE ; schéma : CREATE, USAGE ;
  • table, vue et vue matérialisée : SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER ;
  • séquence : USAGE, SELECT, UPDATE ; fonction et procédure : EXECUTE ; type, domaine, wrapper de données distantes et serveur distant : USAGE.

Chaque case indique d’où provient le privilège :

  • cochée — le rôle le détient directement ; décochez-la pour le révoquer (REVOKE) ;
  • cochée mais désactivée, avec Hérité de : … — le rôle ne le détient que par un autre rôle ou par PUBLIC. Il ne peut pas être révoqué ici ; rendez le rôle source actif (Définir comme rôle actif) et révoquez-le à partir de celui-ci ;
  • non cochée — le rôle ne le détient pas ; cochez-la pour l’accorder (GRANT) directement.

Avec option d’attribution s’applique aux privilèges que vous accordez nouvellement dans cette boîte de dialogue. Validez avec le bouton principal de la boîte de dialogue, qui porte le nom de l’objet.

Pour accorder un privilège sur un objet qui ne figure pas encore dans l’arborescence, utilisez le + (Ajouter un privilège sur un objet) sous la colonne : choisissez le Type d’objet, puis la Base de données (pour tout sauf les bases de données et les tablespaces ; par défaut, la base de données actuelle de la connexion), le Schéma pour les objets de niveau schéma, l’Objet lui-même (les fonctions sont affichées avec la signature de leurs arguments), cochez les Privilèges et, éventuellement, Avec option d’attribution.

Sélectionner PUBLIC dans la première colonne vous permet de modifier ce qui est accordé à PUBLIC lui-même (GRANT … TO PUBLIC / REVOKE … FROM PUBLIC).

Important : chaque action de cette section est exécutée immédiatement sur le serveur — il n’y a ni aperçu SQL ni annulation. Seuls Supprimer le rôle et Retirer l’appartenance demandent d’abord une confirmation. Si le serveur rejette une instruction, son message d’erreur est affiché.
